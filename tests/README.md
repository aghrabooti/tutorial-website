# تست‌های محلی (بدون نیاز به Supabase)

این تست‌ها فانکشن‌های Edge را با یک **دیتابیس درون‌حافظه‌ای** و یک **زرین‌پال تقلبی**
اجرا می‌کنند؛ هیچ درخواست واقعی به Supabase یا زرین‌پال زده نمی‌شود.

```bash
cd tests
npm install        # یک‌بار (esbuild + jsdom)
npm test
```

| تست | چه چیزی را بررسی می‌کند |
|---|---|
| `api-migration.test.mjs` | مسیرهای هم‌مبدأ Next برای دوره‌ها، محتوا، حساب/نشست، سبد، نشانی، دسترسی خرید و APIهای مدیریت (از جمله `admin-shipments`)؛ همچنین اطمینان از عبور درخواست‌های Edge-backed باقی‌مانده از proxy هم‌مبدأ |
| `shipments.test.mjs` | خودترمیمی مرسوله‌های جامانده، عدم ساخت مرسوله برای سفارش‌های دیجیتال/پرداخت‌نشده، گزارش سفارش پستی بدون نشانی همراه شماره تماس، idempotent بودن `resync`، `mark_sent`، کنترل دسترسی مدیر، نمایش خطای دیتابیس |
| `payments.test.mjs` | استفاده از **درگاه واقعی** به‌صورت پیش‌فرض (`payment.zarinpal.com`)، ساخت مرسوله پس از پرداخت موفق، عدم ساخت مرسوله برای اقلام دیجیتال، تشخیص خودکار سندباکس از روی `authority`، تلاش دوباره روی محیط دیگر، خطای واضح در صورت نبود مرچنت‌کد، نیاز به نشانی قبل از پرداخت محصول فیزیکی |
| `admin-panel.test.cjs` | رندر تب‌های پنل مدیریت (کارت وضعیت درگاه، ستون «ارسال پستی»، هشدار مرسوله‌های جامانده و فیلترها) با پاسخ‌های نمونه |

تست‌های routeهای Next.js و build آن‌ها مستقل از این مجموعه اجرا می‌شوند:

```bash
cd apps/next-app
npm ci
npm test
npm run build
```

تست‌های `apps/next-app/test/public-api.test.js`، `auth-session.test.js`، `auth-account.test.js`، `commerce.test.js`، `admin-read.test.js`، `admin-shipments.test.js` و `edge-proxy.test.js` درخواست‌های Supabase را mock می‌کنند و به secret یا پروژه‌ی واقعی نیاز ندارند؛ تست‌های مدیریت شامل نگاشت داده‌ها، بررسی نقش مدیر، عملیات دوره/جلسه، URL آپلود، گزارش وضعیت و همگام‌سازی/ثبت ارسال مرسوله هستند.

نحوه‌ی کار: `build.mjs` هر فانکشن را با esbuild باندل می‌کند، ایمپورت
`https://esm.sh/@supabase/supabase-js@2` را با `supabase-stub.js` جایگزین و
`Deno.env` را با `deno-shim.js` شبیه‌سازی می‌کند. خروجی باندل‌ها در
`tests/.build/` ساخته می‌شود (در گیت نگه داشته نمی‌شود).
